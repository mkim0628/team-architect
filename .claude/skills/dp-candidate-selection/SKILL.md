# DP 후보 구조 선정 (Candidate Structure Selection)

## 목적

설계 포인트(DP)마다 "어떤 구조로 만들 것인가"를 결정하는 과정을 표준화한다.

핵심 원칙: **후보는 메커니즘으로 구별되고, 평가는 QA와 제약에 근거하며, 선정은 재현 가능한 논리로 기록된다.**

이 문서는 팀의 아키텍처 결정 기록(ADR)의 근거가 된다. 나중에 다른 팀원이 읽고 "왜 이 구조를 골랐는지"를 재구성할 수 있어야 하고, 전제 조건이 바뀌었을 때 어떤 후보를 재소환해야 하는지도 알 수 있어야 한다.

## 절차

### 1단계. 컨텍스트 로드

- `docs/01-project-overview.md`를 읽고 대상 DP의 문제 정의, 관련 QA, 환경 제약(Partial DRAM, PLPless), DP 간 연결고리를 파악한다.
- `docs/dp/` 아래 기존 후보 선정 문서가 있으면 읽는다. 이미 선정된 타 DP의 구조는 이번 평가의 전제 조건이 된다.
- 대상 DP가 명시되지 않았으면 요청 문맥에서 추론한다 (예: "저널링" → DP2, "map cache" → DP1, "GC/wear" → DP3).

### 2단계. 후보 도출 (2~4개)

- `references/ftl-catalog.md`에서 해당 DP의 대표 구조 계열을 출발점으로 삼되, 그대로 옮기지 않는다. 본 과제의 제약(Partial DRAM, PLPless, automotive/humanoid 워크로드)에 맞게 구체화한 형태로 기술한다.
- 후보 간에는 **메커니즘 차이**가 있어야 한다. 같은 구조에서 파라미터만 다른 변형은 별도 후보가 아니라 한 후보의 설계 파라미터로 다룬다.
- 탈락시키기 위해 넣는 명백한 straw-man은 넣지 않는다. 모든 후보는 합리적인 팀이 실제로 고려할 만한 수준이어야 한다. 다만 "단순하지만 기준선이 되는 구조"(예: 저널 없이 open block 스캔만으로 복구)는 비교 기준선으로서 가치가 있으므로 포함해도 좋다.
- 각 후보는 세 층위로 기술한다:
  - **구조(정적)**: 구성 요소와 배치 (SRAM/DRAM/NAND 어디에 무엇이 사는지)
  - **동작(동적)**: DP에 유관한 경로 — read / write / flush / SPO dump / open recovery 중 해당되는 것
  - **주요 설계 파라미터**: 이 구조를 채택하면 이후에 튜닝해야 할 값들

### 3단계. 평가

- **결정 기준을 먼저 세운다.** 관련 QA와 환경 제약에서 파생시키되, 가능한 한 측정 가능한 형태로 쓴다 (예: "map miss 1회당 추가 NAND read 수", "SPO 시 dump해야 하는 바이트 수", "flush 1회당 NAND write 양").
- 평가 매트릭스: 후보 × 결정 기준, ◎/○/△/× 4단계. **모든 셀에는 메커니즘에 근거한 이유가 붙어야 한다.** 근거 없는 점수는 쓰지 않는다 — 점수보다 근거가 본체다.
- 제약 적합성은 매트릭스와 별도로 점검한다:
  - Partial DRAM: 상주 자료구조가 메모리 예산 안에 들어가는가, 예산 초과 시 어떻게 degrade되는가
  - PLPless: SPO 시 dump해야 하는 양이 잔여 에너지 예산 안인가
- 수치를 가정할 때는 가정임을 명시한다 (예: "4KB map page = 1024 entries, 1TB 기준 GTD 약 1MB 가정").

### 4단계. Trade-off / 민감도 분석

- 어떤 조건(워크로드 패턴, 파라미터 값, QA 목표 수치)에서 후보 간 우열이 **뒤집히는지**를 명시한다. 어떤 조건에서도 우열이 안 바뀌는 기준은 결정 기준으로서 의미가 약하다 — 뒤집히는 지점이 곧 팀이 확정해야 할 요구사항이다.
- 타 DP와의 상호작용: 이 선택이 다른 DP의 설계 공간을 어떻게 제한하거나 넓히는지 기술한다 (예: L2P 캐시의 dirty 총량 상한 → 저널링의 dump 예산을 결정).

### 5단계. 선정

- 권고안을 명확히 낸다. 조건부 선정도 허용된다 (예: "open recovery 상한이 N초 이하로 확정되면 후보 B, 아니면 후보 A").
- 확정할 수 없으면 **결정을 확정하기 위해 필요한 정보/실험**을 구체적으로 남긴다 (필요한 워크로드 데이터, 시뮬레이션, 확정해야 할 목표 수치).
- 채택되지 않은 후보의 탈락 사유도 기록한다. 전제가 바뀌면 재소환할 근거가 된다.

### 6단계. 산출물 저장

- `docs/dp/dp<N>-<slug>-candidates.md`로 저장한다 (예: `docs/dp/dp1-l2p-cache-candidates.md`).
- `README.md`의 문서 표에 행을 추가한다.
- 아래 문서 템플릿을 그대로 따른다.

## 문서 템플릿

ALWAYS use this exact structure:

```markdown
# DP<N>. <DP 이름> — 후보 구조 선정

## 1. 문제 정의
(DP가 해결하려는 문제, 관련 QA, 환경 제약 — overview 요약 + 이 문서 수준으로 구체화)

## 2. 결정 기준
(번호 붙인 기준 목록. 각 기준의 출처(QA/제약)와 측정 방법)

## 3. 후보 구조

### 후보 A. <이름>
- **개요**: 한 문단
- **구조**: 구성 요소와 배치 (mermaid 다이어그램 권장)
- **동작**: 유관 경로별 동작 (read / write / flush / SPO dump / recovery 중 해당분)
- **주요 설계 파라미터**: 표
- **강점** / **약점·리스크**

(후보 B, C … 동일 구조)

## 4. 평가

### 4.1 평가 매트릭스
(후보 × 결정 기준 표, ◎○△× + 셀별 근거)

### 4.2 제약 적합성
(Partial DRAM / PLPless 각각 후보별 점검)

### 4.3 Trade-off 및 민감도
(우열이 뒤집히는 조건)

## 5. 타 DP와의 상호작용
(이 선택이 다른 DP에 거는 제약/전제)

## 6. 선정 결과
- **권고**: 후보 X (조건이 있으면 조건 명시)
- **근거**: 결정 기준 기준 요약
- **탈락 사유**: 채택되지 않은 후보별
- **후속 검증 항목**: 확정에 필요한 정보/실험
```

## 품질 기준

- 근거 없는 평가 셀 금지. "좋다/나쁘다"가 아니라 "어떤 메커니즘 때문에 그 결과가 나오는지"를 쓴다.
- 문헌 구조 이름(DFTL 등)을 언급할 때는 논문 요약이 아니라 이 과제 맥락으로 각색한 우리 설계의 후보로 기술한다.
- 한국어로 쓰되 기술 용어는 영문을 유지한다 (프로젝트 문서 관례).
- 다이어그램은 mermaid를 사용한다.
- QA 번호(QA1~QA5), DP 번호(DP1~DP3)는 `docs/01-project-overview.md`의 정의를 따른다.
