# DP 단점 보완 Tactic 탐색 (Tactic Refinement)

## 목적

후보 구조 선정(`dp-candidate-selection`)이 끝나면 채택된 구조에는 반드시 단점이 남는다 — 두 후보 중 하나를 고르는 것은 그 후보의 단점을 감수하기로 한 결정이기 때문이다. 이 스킬은 그 남은 단점을 **architectural tactic으로 보완**하는 과정을 표준화한다.

핵심 원칙: **tactic은 공짜가 아니다.** 모든 tactic은 다른 QA에 부작용을 만들 수 있으므로, "단점이 얼마나 완화되는가"와 "무엇이 새로 나빠지는가"를 항상 쌍으로 평가한다. 보완 후에도 남는 잔여 리스크를 정직하게 기록하는 것이 이 문서의 가치다.

## 절차

### 1단계. 입력 확보

- `docs/01-project-overview.md`와 대상 DP의 후보 선정 문서(`docs/dp/dp<N>-*-candidates.md`)를 읽는다.
- 분석 대상은 원칙적으로 **채택된 후보의 단점 목록**이다. 사용자가 특정 단점만 지목하면 그것만 다루되, 문서에 있는 나머지 단점도 목록으로 확인해 준다.
- 후보 선정 문서가 없으면: 대화에서 단점을 직접 수집하거나, 먼저 `dp-candidate-selection`을 수행할지 사용자에게 확인한다.

### 2단계. 단점 특성화

각 단점을 다음 형식으로 정리한다. 이게 정확해야 tactic 탐색이 산으로 가지 않는다.

- **무엇이**: 어떤 메커니즘이
- **언제**: 어떤 조건/워크로드에서
- **어떤 QA를**: QA1~QA5 중 무엇을 얼마나 해치는지 (가능하면 정량 — 추가 NAND read/write 횟수, dump 바이트, 스캔량 등으로 환산)

### 3단계. Tactic 탐색 (단점당 2~3개)

- `references/tactics-catalog.md`의 tactic 분류(일반 아키텍처 tactic + FTL 도메인 기법)를 훑으며 해당 단점에 적용 가능한 tactic을 브레인스토밍한다. 카탈로그에 없는 tactic을 고안해도 된다 — 카탈로그는 사고를 넓히는 체크리스트지 한계가 아니다.
- 서로 다른 접근 계열에서 뽑는다. 예: 같은 단점에 대해 "자원을 더 쓰는 tactic"(캐시 증설), "일을 미루는 tactic"(지연·배치), "일을 줄이는 tactic"(압축·필터링)은 서로 다른 계열이다. 한 계열에서만 3개를 뽑으면 탐색이 아니라 변주다.
- 각 tactic은 다음을 기술한다:
  - **메커니즘**: 무엇을 어떻게 바꾸는가
  - **보완 효과**: 단점이 어느 정도 완화되는가 (2단계의 정량 축으로)
  - **부작용**: 다른 QA·제약(Partial DRAM 메모리, PLPless dump 예산)에 미치는 영향
  - **구현 복잡도·리스크**: 상/중/하 + 이유

### 4단계. 평가 및 권고

- Tactic 평가 요약 표를 만든다: tactic × (보완 효과 / 부작용 / 복잡도 / 채택 권고).
- **채택 권고 조합**을 낸다: 어떤 tactic을 채택하고, 어떤 것은 조건부(어떤 수치가 확정되면)로 미루고, 어떤 것은 기각하는지. 서로 배타적인 tactic이 있으면 명시한다.
- 보완 후에도 남는 **잔여 리스크**와, 그것을 감수 가능하다고 판단한 근거를 기록한다.
- 채택 tactic이 타 DP 설계에 거는 새 제약이 있으면 명시한다.

### 5단계. 산출물 저장

- `docs/dp/dp<N>-<slug>-tactics.md`로 저장한다 (예: `docs/dp/dp2-journaling-tactics.md`).
- `README.md`의 문서 표에 행을 추가한다.
- 아래 템플릿을 그대로 따른다.

## 문서 템플릿

ALWAYS use this exact structure:

```markdown
# DP<N>. <DP 이름> — 단점 보완 Tactic 분석

## 1. 대상 구조와 단점 요약
(채택 후보와 그 단점 목록. 단점마다: 메커니즘 / 발생 조건 / 해치는 QA와 정량 영향)

## 2. 단점별 Tactic 탐색

### 단점 1: <이름>
| Tactic | 메커니즘 | 보완 효과 | 부작용 | 복잡도 |
|---|---|---|---|---|
(tactic별 상세 설명은 표 아래 서술)

### 단점 2: … (동일 구조)

## 3. Tactic 평가 요약
(전체 tactic × 보완 효과/부작용/복잡도/채택 권고 표)

## 4. 권고 조합
- **채택**: tactic 목록 + 근거
- **조건부**: 어떤 정보가 확정되면 채택할지
- **기각**: 사유
- **적용 후 구조**: 채택 tactic이 반영된 구조의 최종 모습 (필요시 mermaid)
- **잔여 리스크**: 보완 후에도 남는 것과 감수 근거

## 5. 타 DP 영향
(채택 tactic이 다른 DP에 거는 새 제약/전제)
```

## 품질 기준

- 보완 효과와 부작용은 반드시 쌍으로 기술한다. 부작용 없는 tactic으로 서술된 것은 대개 분석이 덜 된 것이다.
- 효과는 가능한 한 2단계에서 세운 정량 축(추가 NAND 접근, dump 바이트, WAF 기여분 등)으로 환산해 비교한다.
- QA·DP 번호는 `docs/01-project-overview.md`의 정의를 따른다. 한국어로 쓰되 기술 용어는 영문을 유지한다.
